# Постоянный вход выбранной установки

[Пошаговая инструкция](#пошаговая-инструкция).

В версии 3.0.0 одна пакетная команда обслуживает разные проекты. После однократной
подготовки пакета и конфигов выполните из каталога нужного проекта:

```bash
start-app infra
start-app deps
start-app adjust
start-app check
start-app run
```

Каждая операция вызывается отдельно. `infra` устанавливает и настраивает инфраструктуру,
`deps` — зависимости, `adjust` согласует настройки, `check` проверяет ресурсы и связанные
условия, `run` выполняет объявленные команды запуска. Порядок команд задают конфиги проекта.

## Выбор установки и рабочего файла

Оператор устанавливает выбранные байты пакета и предоставляет его `bin` в `PATH`.
Исполняемый файл, Python и библиотеки принадлежат установленному инструменту.
Проект предоставляет постоянные конфиги и свои прикладные CLI-инструменты.
Один пакетный вход используется одинаково для ERP, Poise и другого проекта.

Без `--config` общий CLI читает `start-app.json` в текущем каталоге вызывающего процесса.
Расположение установленного Python определяет runtime инструмента; текущий каталог
определяет обслуживаемый проект. Абсолютный путь к пакетной команде выбирает тот же
runtime и сохраняет этот договор выбора проекта.

| Вход | Runtime | Главный файл обычного вызова |
|---|---|---|
| Пакетный `start-app` из `PATH` | Собственная `.venv` выбранного пакета | `CWD/start-app.json` |
| Абсолютный путь к пакетному входу | Тот же выбранный runtime | `CWD/start-app.json` |
| Корневой вход исходного комплекта инструмента | Его установленная `.venv` | `CWD/start-app.json` |

Вызов из другого каталога выбирает нужный main через необязательный `--config`.
Проектные загрузчики, обёртки, парсеры и диспетчеры для подключения не требуются.

## Поля постоянного профиля

[Заполнение и проверка](#пошаговая-инструкция).

Обезличенный [главный пример](../examples/persistent-entry/start-app.example.json)
сопоставляет каждой операции документ через `operations`. Имена и пути этих документов
задаются в main. `interpreters` выбирает готовые обработчики результатов по
[договору действий](action-execution.md#интерфейс-интерпретатора).

```json
"invocation": {
  "parameters": "parameters.json",
  "base_dir": ".",
  "requirements": {
    "infra": ["assets"],
    "deps": ["packages"],
    "adjust": ["alignment"],
    "run": ["launcher"]
  }
}
```

| Поле | Значение |
|---|---|
| `invocation.parameters` | Непустой путь к JSON-объекту значений |
| `invocation.base_dir` | Непустой путь к базе относительных `cwd` команд |
| `invocation.requirements.OPERATION` | `all` либо массив IDs для infra/deps/adjust/run |

`all` использует порядок документа; массив сохраняет заданный порядок и повторы.
`[]` явно выбирает пустой список. `check` читает ресурсы infra/deps и дополнительные
условия check: presence и предоставленную availability выполняет по
[договору проверки](resource-checking.md#проверка-окружения).

Шаблоны argv/cwd/env обрабатывает стандартный `string.Template`. Внешние программы,
аргументы, каталоги, значения и порядок принадлежат конфигам; единый исполнитель
пакета запускает команды и передаёт их полные результаты выбранным обработчикам.

Для сетевого `adjust` выберите сетевые требования; командные действия запускайте
отдельной выборкой. Полная [декларация и пример двух серверов](settings-alignment.md#два-http-сервера)
принадлежат инструкции согласования. Подстановки из карты в библиотеке остаются
командным API и не задают путь для сетевой записи.

Рабочий профиль и данные хранятся у проекта вне `.runtime` и исключаются из Git.
В Git остаются заполненные обезличенные примеры. Очистка временных материалов
сохраняет постоянные настройки.

## Переопределение одного вызова

[Правильные вызовы](#необязательные-переопределения).

Явные ключи переопределяют соответствующие сохранённые значения только для текущего
вызова. Остальные значения берутся из выбранного main; следующие обычные вызовы
из каталога проекта используют его прежний профиль. Выбор переопределения
не переписывает `main` и его `invocation`. Сама выбранная операция может сохранять
свои данные: [сетевой adjust](settings-alignment.md#автоматический-подбор-портов)
обновляет выбранный файл параметров, сохраняя согласованные порты и адреса.

| Значение | Источник | База относительного пути |
|---|---|---|
| Главный файл | `--config` либо `start-app.json` текущего каталога | Cwd вызывающего |
| Параметры | `--parameters` либо `invocation.parameters` | Ключ — cwd; поле — каталог main |
| База команд | `--base-dir` либо `invocation.base_dir` | Ключ абсолютный; поле — каталог main |
| Выбор ресурсов | `--requirements` либо поле операции | `all` или массив IDs |
| Документ операции | `operations.OPERATION` | Каталог выбранного main |

Для настроенного `check` ресурсы определяются его договором, без `--requirements`.
Полностью явная форма с необходимыми ключами работает с main без `invocation`.
Библиотечные аргументы остаются явными: [подготовка](resource-preparation.md#библиотечный-вход)
и [проверка](resource-checking.md#библиотечный-вход).
Явные `check/run --catalog-dir` используют отдельный
[каталоговый договор](configuration.md#команды-и-аргументы), независимо от обычного main.

## Пошаговая инструкция

### Однократная подготовка оператором

1. Установите выбранный пакет по [npm-инструкции](npm-distribution.md#пошаговая-инструкция).
   Предоставьте каталог его `bin` через `PATH`; проверьте `start-app --version`.
   Выберите существующий каталог обслуживаемого проекта.
2. Подготовьте объявленные внешние CLI-инструменты и выбранные обработчики результатов.
   Готовый общий обработчик кода завершения поставляется в
   [примере инструмента](../examples/resource-preparation/interpreters.py).
   Обработчик устанавливается в собственный runtime SDK. Его выбирают через main,
   а прикладные команды — через документы операций.
3. Для учебного профиля заполните копию
   [параметров](../examples/persistent-entry/parameters.example.json): `python` — выбранный
   Python, `probe` — поставленный [учебный CLI](../examples/resource-preparation/probe.py),
   `events` — собственный файл данных. `token` равен `demo value`, `state` — `ready`.
4. Включите [готовую декларацию](../examples/persistent-entry/deploy.example.json)
   в deps существующего владельца развёртывания через
   [библиотеку конфигурации](configuration-editing.md#пошаговая-инструкция).
   Его реестр предоставляет обработчик `result`, принимающий код 0. Заполните
   [параметры подготовки](../examples/persistent-entry/deploy-parameters.example.json):
   `copy` — стандартный `cp`, `example_root` — примеры установленного SDK,
   `project_root` — существующий отдельный каталог учебного проекта,
   `package_root` — выбранный пакет, `filled_parameters` — заполненный рабочий JSON.
   `interpreter_source` — поставленный обработчик, `interpreter_target` —
   `interpreters.py` в собственном `purelib` этого SDK.

   ```bash
   /absolute/path/to/package/.venv/bin/python -I -B -c 'import sysconfig; print(sysconfig.get_path("purelib"))'
   ```

5. Выполните deps владельца с требованием `persistent-entry`. Декларация публикует
   семь рабочих JSON в `project_root` и обработчик в выбранный SDK runtime.
   В реальном проекте конфиги содержат его инструменты и значения.

Учебный профиль используется в отдельном каталоге и записывает демонстрационные
события. Рабочие ERP/Poise настраиваются с сохранением их собственных данных;
проверка учебного профиля не подтверждает их развёртывание.

### Пять обычных операций

Из `project_root` выполните пять коротких команд в начале страницы. Для учебного
профиля каждая возвращает код 0 и JSON с `status: succeeded`. В `events` появятся:

```text
install
configure
dependencies
align
infra-presence
infra-availability
deps-presence
consistency
run
```

У deps предоставлена presence; availability помечается `not_configured`.
Последний `run` добавляет только событие запуска. Сам `start-app` и его runtime
остаются в пакетной установке; проект содержит семь JSON-конфигов.

### Необязательные переопределения

В каталоге проекта подготовьте `other-values.json` с теми же путями и другим token:

```bash
start-app deps --parameters other-values.json
start-app deps
```

Первая запись `dependencies` содержит новый token, следующая — `demo value`.
Оба рабочих файла сохраняются. Другой main и отдельный ресурс выбираются явно:

```bash
start-app deps --config /absolute/path/to/other/start-app.json
start-app infra --requirements '["assets"]'
```

Из постороннего cwd укажите абсолютный main через `--config`.
Для последующего обычного вызова перейдите в каталог выбранного проекта.

### Сохранение и новая поставка

Постоянные рабочие конфиги и данные принадлежат проекту. Оператор устанавливает
проверенные байты нового SDK и проверяет проект до переключения используемого
пакетного входа. Примеры и справка находятся в пакете; рабочие настройки — у проекта.

В 3.0 главный файл обычного вызова выбирается из cwd проекта; в 2.1 он выбирался
рядом с runtime инструмента. При переходе опубликуйте main в каталоге проекта
с его существующими значениями. Согласуйте относительные `operations`,
`invocation.parameters` и `invocation.base_dir` с расположением main так, чтобы они
указывали на прежние нужные файлы и ресурсы. Сохраните прочие поля и данные.
Проверьте пять операций и переопределения выбранным пакетом. Пакет предоставляет
одну команду для всех проектов; проектные адаптеры исключаются из обычного запуска.
Предыдущие выпущенные байты сохраняют свою идентичность.

## Результат и диагностика

Код 0 означает успех, 1 — ошибку выполненной цепочки с частичным результатом,
2 — ошибку входного договора с диагностикой. Результат содержит полные stdout/stderr
и коды реально выполненных команд. Неуспех останавливает затронутую цепочку;
`check` собирает результаты независимых проверок.

Диагностика называет выбранный файл и недостающие настройки. Исправьте их
существующим владельцем конфигурации и повторите осознанный вызов.
Сменные обработчики описаны в [договоре исполнения](action-execution.md#интерфейс-интерпретатора).

# Постоянный вход выбранной установки

[Пошаговая инструкция](#пошаговая-инструкция).

В версии 2.1.0 обычный вызов состоит из локального входа и операции.
После однократной настройки выбранной установки:

```bash
./start-app infra
./start-app deps
./start-app adjust
./start-app check
./start-app run
```

`infra` подготавливает инфраструктуру, `deps` — зависимости, `adjust` согласует
настройки, `check` наблюдает готовность, `run` запускает объявленные команды.
Порядок обслуживания задаёт приложение. Каждая операция вызывается отдельно.
Конкретные установщики, диагностику и обработчики результатов предоставляет
обслуживаемое приложение; общий исполнитель читает их декларации.

## Выбор установки и рабочего файла

Вызовите `./start-app` из каталога входа выбранной установки либо укажите
абсолютный путь к этому входу из другого каталога. У каждой установки свои
настройки, данные и выбранный SDK. Рабочий каталог вызывающего сохраняется.

Без `--config` главный файл называется `start-app.json`. Его каталог — родитель
собственного `sys.prefix` выбранного Python. Поддерживаемая структура:

| Вход | Собственный runtime | Главный рабочий файл |
|---|---|---|
| Корневой `start-app` исходного комплекта | `ROOT/.venv` | `ROOT/start-app.json` |
| Npm-вход `PREFIX/bin/start-app` | `PACKAGE_ROOT/.venv` | `PACKAGE_ROOT/start-app.json` |

`PACKAGE_ROOT` получают командой `npm root --global --prefix PREFIX`, добавив
`environment-maintenance`. Он отличается от каталога `PREFIX/bin`.
Npm-вход и корневой вход используют установленный пакет своей среды.
При работе из исходников сначала установите выбранную ревизию в эту среду.

## Поля постоянного профиля

[Заполнение и проверка](#пошаговая-инструкция).

Обезличенный [главный пример](../examples/persistent-entry/start-app.example.json)
сопоставляет каждой операции отдельный документ через `operations`.
`interpreters` содержит имена модулей и готовых объектов обработчиков
по [договору действий](action-execution.md#интерфейс-интерпретатора).

```json
"invocation": {
  "parameters": "parameters.json",
  "base_dir": ".",
  "requirements": {
    "infra": ["assets"],
    "deps": ["packages"],
    "adjust": ["alignment"],
    "run": ["launcher"]
  }
}
```

| Поле | Значение |
|---|---|
| `invocation.parameters` | Непустой путь к одному JSON-объекту скалярных значений |
| `invocation.base_dir` | Непустой путь к базе относительных `cwd` команд |
| `invocation.requirements.OPERATION` | `"all"` либо массив IDs для infra/deps/adjust/run |

`all` использует порядок документа; массив сохраняет заданный порядок и повторы.
`[]` явно выбирает пустой список. Для `check` ресурсы определяются документами
infra/deps и дополнительными условиями check. Проверка наличия и предоставленная
проверка доступности описаны в [договоре проверки](resource-checking.md#проверка-окружения).

Рабочий профиль принадлежит приложению, хранится вне `.runtime` и исключается
из Git. В Git остаются только заполненные обезличенными значениями примеры.
Оператор исключает также собственные нестандартные имена рабочих файлов.
Очистка временных материалов не меняет эти настройки.

## Переопределение одного вызова

[Правильные вызовы](#необязательные-переопределения).

Все прежние рабочие ключи доступны как необязательные переопределения.
Незаданные значения берутся из выбранного главного файла. Переопределения
не записываются обратно; следующий обычный вызов использует прежний профиль.

| Значение | Откуда берётся | База относительного пути |
|---|---|---|
| Главный файл | `--config` либо обычный `start-app.json` | Явный ключ — cwd вызывающего |
| Параметры | `--parameters` либо `invocation.parameters` | Ключ — cwd; поле — каталог main |
| База команд | `--base-dir` либо `invocation.base_dir` | Ключ абсолютный; поле — каталог main |
| Выбор ресурсов | `--requirements` либо поле текущей операции | `all` или массив IDs |
| Документ операции | `operations.OPERATION` | Каталог выбранного main |

Полностью явный вызов с необходимыми ключами работает и с главным файлом
без блока `invocation`. В API аргументы остаются явными: договор функций
описан у [подготовки](resource-preparation.md#библиотечный-вход)
и [проверки](resource-checking.md#библиотечный-вход).
Явные каталоговые `check/run --catalog-dir` выбирают отдельный
[каталоговый договор](configuration.md#команды-и-аргументы), в том числе
при наличии обычного `start-app.json`.

## Пошаговая инструкция

### Однократная подготовка оператором

1. Установите выбранные байты пакета в собственный prefix по
   [npm-инструкции](npm-distribution.md#пошаговая-инструкция).
   Зафиксируйте каталог пакета, собственный Python и локальный вход.
2. Приложение предоставляет внешние команды и готовый обработчик результатов.
   Подготовьте их через его настроенного владельца развёртывания и конфиг.
   Обработчик должен импортироваться собственным Python выбранного SDK.
   Корневой вход использует `-I`; npm-вход — `-P -s -B` и стандартный путь
   импорта. Доступность обработчика является частью подготовки приложения.
3. Для учебного профиля заполните копию
   [параметров](../examples/persistent-entry/parameters.example.json): `python`
   указывает собственный Python, `probe` — поставленный
   [учебный инструмент](../examples/resource-preparation/probe.py), `events` —
   файл в собственном каталоге данных. `token` равен `demo value`, `state` — `ready`.
4. Включите [декларацию подготовки](../examples/persistent-entry/deploy.example.json)
   в deps существующего владельца развёртывания через
   [библиотеку конфигурации](configuration-editing.md#пошаговая-инструкция).
   Его реестр предоставляет обработчик `result`, принимающий код 0.
   Заполните [параметры подготовки](../examples/persistent-entry/deploy-parameters.example.json).
   `copy` — выбранный стандартный `cp`, `example_root` — каталог этих примеров,
   `package_root` — выбранный пакет, `filled_parameters` — заполненный рабочий JSON.
   `interpreter_source` — поставленный
   [обработчик](../examples/resource-preparation/interpreters.py),
   `interpreter_target` — файл `interpreters.py` в собственном `purelib` SDK.
   Точный `purelib` оператор узнаёт у выбранного Python через стандартный `sysconfig`:

   ```bash
   /absolute/path/to/package/.venv/bin/python -I -B -c 'import sysconfig; print(sysconfig.get_path("purelib"))'
   ```
5. Запустите deps этого владельца с выбранным требованием `persistent-entry`.
   Объявленные команды копирования создадут `start-app.json`, `parameters.json`,
   пять документов операций и готовый обработчик в выбранной установке.
   Для реального приложения его профиль использует собственные инструменты.

Учебный инструмент записывает события и возвращает наблюдаемые потоки/код.
Он демонстрирует исполнение цепочек, а не установку реальной БД или ERP.
Все пути и действия подготовки находятся в конфиге владельца; пользователь
получает уже подготовленный локальный вход.

### Пять обычных операций

В каталоге локального входа выполните пять коротких команд из начала страницы.
Ожидаются код 0 и JSON с `status: succeeded` для каждой операции.
В файле `events` последовательно появятся метки:

```text
install
configure
dependencies
align
infra-presence
infra-availability
deps-presence
consistency
run
```

У deps здесь предоставлена presence; доступность помечается `not_configured`.
Последний `run` добавляет только метку `run` и не повторяет подготовку.
Из постороннего каталога тот же профиль использует абсолютный выбранный вход:

```bash
/absolute/path/to/selected/bin/start-app run
```

### Необязательные переопределения

Подготовьте собственный `other-values.json` с теми же путями и другим `token`.
Из его каталога выбранным абсолютным входом:

```bash
/absolute/path/to/selected/bin/start-app deps --parameters other-values.json
/absolute/path/to/selected/bin/start-app deps
```

Первая запись `dependencies` содержит новый token, следующая — `demo value`.
Рабочий профиль сохраняется. Выбор отдельного ресурса или другого main:

```bash
./start-app infra --requirements '["assets"]'
./start-app deps --config /absolute/path/to/other/start-app.json
```

### Сохранение и новая поставка

Сохраняйте рабочие профили и данные у обслуживаемого приложения.
Новый выбранный пакет устанавливает его владелец развёртывания по конфигу,
переносит необходимые настройки и проверяет выбранную установку до переключения.
Npm управляет содержимым установленного пакета; его удаление не является
способом хранения единственной копии рабочего профиля.

При общей установке SDK приложение предоставляет свой локальный вход,
внутренне привязанный к постоянному main приложения через явный `--config`.
Пользовательские аргументы следуют после этой привязки, поэтому остаются
необязательными переопределениями текущего вызова. Cwd и выбранная установка
сохраняются. Это договор подключения; фактическую готовность ERP и Poise
подтверждают их собственные проверки поставки.

## Результат и диагностика

Код 0 означает подтверждённый успех операции, 1 — ошибку исполненной цепочки
с уже попытанными действиями, 2 — ошибку входного договора с диагностикой.
Отсутствующий или непригодный нужный параметр сообщает путь main и поле.
Прочитайте полный результат, исправьте объявленную причину у владельца
настроек/инструмента и выполните осознанный следующий вызов.
Сменные обработчики и дальнейшие действия принадлежат
[договору исполнения](action-execution.md#интерфейс-интерпретатора).

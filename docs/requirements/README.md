# Источники начальных требований

Это исходные материалы требований разработки выбранного Poise-проекта EM.
Приложение `environment-maintenance` исполняется независимо от Poise и его баз.

| Источник | Назначение |
|---|---|
| [schema.sql](schema.sql) | Точная начальная схема выбранного владельца миграций Poise |
| [0001_em_port_agreement.sql](data/0001_em_port_agreement.sql) | Начальные данные: одно System-требование, четыре Application-требования, четыре связи и revision 1 |
| [0001_em_port_agreement.rollback.sql](data/0001_em_port_agreement.rollback.sql) | Согласованный обратный шаг именно этих начальных данных |
| [0002_em_local_dependencies.sql](data/0002_em_local_dependencies.sql) | Независимые зависимости приложений: одно System-требование, четыре Application-требования, четыре связи и revision 2 |
| [0002_em_local_dependencies.rollback.sql](data/0002_em_local_dependencies.rollback.sql) | Обратный шаг второй миграции с сохранением начальных данных |
| [0003_em_application_processes.sql](data/0003_em_application_processes.sql) | Именованные операции приложений: одно System, четыре Application, четыре связи, revision3 |
| [0003_em_application_processes.rollback.sql](data/0003_em_application_processes.rollback.sql) | Обратный шаг третьей миграции с сохранением предыдущих данных |

Третья миграция связывает объявленное обслуживание, запуск по окружениям, учёт/остановку групп и инструкции. Её seed сущности имеют status future; это source материала требований, а не автоматическая приёмка реализованной возможности. Рабочая база на этапе документации не изменяется.

Начальные сущности описывают разрешение конфликта сетевых адресов, подбор порта,
согласование зависимых адресов, стабильность назначения и сохранность при отказе.
Их статус `future` фиксирует начальный каталог. Доставка seed не переводит сущности
в принятые или реализованные и не заменяет текущий реестр требований, Task snapshot
или независимую приёмку результата.

Вторая миграция описывает собственный экземпляр зависимости приложения,
воспроизводимое восстановление выбранной версии, независимость других приложений
и использование принадлежащих приложению инструментов. Эти предложенные сущности
также имеют статус `future`; их регистрация и приёмка конкретной поставки различаются.

В выбранной внешней конфигурации проекта `paths.requirements_schema_migrations`
выбирает историю схемы Poise, `paths.requirements_data_migrations` — эту `data`,
а `paths.requirements_schema_file` — этот `schema.sql`. Рабочая конфигурация и база
хранятся вне Git. Имена/байты источников исходной редакции сохраняются; изменение
данных оформляет существующий публичный владелец требований новой миграцией.
Прямое исполнение SQL в рабочей базе не является инструкцией подготовки.

Создание новой базы принадлежит инфраструктурному владельцу
`poise_environment.repairs.requirements_database`: он использует
`RequirementsMigrations.initialize` с выбранными непустыми историями схемы и данных.
Проверка `maintain(..., action="check", ...)` создаёт собственную временную эталонную
базу через того же инициализатора и наблюдает выбранную рабочую базу.
Существующая база при этом не пересоздаётся и не исправляется.

При проверке Task worktree источники данных выбираются из его `docs/requirements/data`
по правилу существующего владельца путей. Это проверка конкретного кандидата.
Она не подменяет пути основного checkout, не публикует конфигурацию и не доказывает
потребление новых исходников установленным профилем. Основной checkout получает
материалы только после отдельно разрешённой интеграции; дальнейшее развёртывание
подтверждает его владелец. Отдельно различаются исходники, проверка базы, готовность
задачи и приёмка/поставка результата.

Фактический пользовательский договор сетевого согласования находится в
[руководстве adjust](../settings-alignment.md#автоматический-подбор-портов),
а ответственность исходных модулей — в [руководстве разработки](../development.md#ответственность-модулей).

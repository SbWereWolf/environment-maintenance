# Разработка и выпуск

## Подготовка

В самостоятельном исходном корне с Python 3.11+:

```bash
python3 -m venv --copies .venv
.venv/bin/python -m pip install '.[dev]'
mkdir -p build
```

`dev` устанавливает `build`, `pytest`, `setuptools>=65` и `wheel`; стандартные
зависимости этих инструментов устанавливает Python-пакетный менеджер. Для работы
установленного приложения они не требуются. `.venv`, `build`, `dist`,
`*.egg-info` и кеши исключены из Git. Рабочие материалы экземпляра остаются
в собственном корне и не становятся частью исходной поставки.

## Ответственность модулей

`cli.main` читает CLI и печатает итог; `__main__` и два консольных имени вызывают
тот же вход. Корневой `start-app` выбирает собственную установленную `.venv`.
`catalogue` проверяет входную схему; `parameters` разрешает значения и подстановки;
`engine` выбирает действия по состоянию ресурса; `process` выполняет внешний процесс
и разбирает его ответ. Предметная логика обслуживания находится в этих владельцах,
а инструменты конкретной инфраструктуры задаются каталогом.

Изменение поведения разрабатывается через TDD: согласовать проверку, написать
воспроизводящий тест и подтвердить RED, независимо проверить тест, реализовать
поведение, подтвердить GREEN и передать точную ревизию на независимую проверку.
Исправление принятого теста согласуется с проверяющим отдельно от реализации.
Документация обновляется по фактическому принятому поведению.

## Проверки

Команды из исходного корня; установленный `dev` обеспечивает средства сборки:

```bash
PYTHONPATH=src .venv/bin/python -B -m pytest -p no:cacheprovider -q \
  tests/test_v1_release.py --basetemp build/release-check
PYTHONPATH=src bash tests/smoke.sh .venv/bin/python
PYTHONPATH=src .venv/bin/python -B -m pytest -p no:cacheprovider -q \
  tests/test_v2_documentation.py
```

Целевой набор содержит 29 случаев: версия, аргументы и результаты обоих входов,
реальная сборка wheel/sdist, установка wheel в собственную `.venv` временного
потребителя, наличие собственных документации/тестов в исходном архиве и
сохранение действующего каталога v2. Smoke содержит 24 случая; две проверки
документационного договора дополняют содержательное чтение инструкций.
Последовательные запуски сборочных тестов используют разные `--basetemp`, если
нужно сохранить предыдущие результаты. Одновременно запущенные сборки одного
исходного дерева не являются способом проверки поставки.

Проверка текста или ссылки не доказывает исполнение команды: отдельно выполните
установку и примеры `--version`/`check` по [инструкции](installation.md), в том числе
из постороннего cwd. Проверьте локальные ссылки, точные заголовки и входящие ссылки
применяемым инструментом проверки документации проекта, а смысл — по коду и
полным результатам. Исторические сценарии восстановления прежних выпусков
сохранены в `tests`; их наличие не означает выполнение в новом выпуске.

## Сборка и поставка

Зафиксируйте точную ревизию исходников, включая документы. Стандартная сборка
в подготовленном окружении:

```bash
.venv/bin/python -m build --no-isolation --outdir dist/1.0.0
sha256sum dist/1.0.0/environment_maintenance-1.0.0-py3-none-any.whl \
  dist/1.0.0/environment_maintenance-1.0.0.tar.gz
```

Исходный архив включает корневой вход, исходники, README, `pyproject.toml`,
примеры, документацию и тесты. Wheel предназначен для установки: собственные
консольные входы создаёт `pip`. Проверяйте те же выбранные байты пакетов, которые
передаются получателю, а не только заново собранный аналог.

Изменение документации после сборки требует новой сборки исходного архива и
новых доказательств для окончательной ревизии. Сохраните отдельно от архивов
квитанцию: версия, точный commit/tree и tag, имена и SHA-256 wheel/sdist,
инструменты и команды сборки, полные stdout/stderr и результаты проверок,
приёмка и интеграция. Свяжите содержимое модулей wheel и исходного архива с
этой ревизией. Квитанция не включается внутрь архива, чей digest она описывает.

После независимой приёмки интегрируйте принятую ревизию в основной checkout.
Установите выбранный wheel в его собственную `.venv` и проверьте корневой
`start-app --version` и `check`. Успех временного потребителя не заменяет этот шаг.
Создайте локальный tag `v1.0.0` на точной интегрированной ревизии после проверки,
что такого tag ещё нет. Сохраните wheel/sdist, квитанцию и журналы в постоянном
каталоге `dist/1.0.0` самостоятельного приложения до удаления материалов задачи.

Локальная поставка — отдельный результат после сборки, проверки, приёмки,
интеграции и подтверждения установки. Текущий способ передачи — этот комплект
файлов; публикация в реестре и отправка Git в сеть являются отдельными действиями.
Правила изменения версии определены в [README](../README.md#версионирование).

# Разработка и выпуск

## Подготовка

В отдельном исходном checkout с Python 3.11+:

```bash
python3 -m venv --copies .venv
.venv/bin/python -m pip install '.[dev]'
mkdir -p build
```

`dev` устанавливает `build`, `pytest`, `setuptools>=65` и `wheel`; стандартные
зависимости этих инструментов устанавливает Python-пакетный менеджер. Для работы
установленного приложения средства разработки не требуются. Текущие исходники
записи дополнительно объявляют runtime-зависимости `jsonpatch>=1.36` и
`jsonpointer>=3.4`; `pip install '.[dev]'` устанавливает и их. `.venv`, `build`, `dist`,
`*.egg-info` и кеши исключены из Git. Рабочие материалы экземпляра остаются
в собственном корне и не становятся частью исходной поставки.

Для проверок выберите подготовленный Python своего development checkout
с объявленными runtime/dev зависимостями:

```bash
app_python=/absolute/path/to/development-checkout/.venv/bin/python
```

При проверках ниже замените `.venv/bin/python` этим фактическим путём, задавая
`PYTHONPATH=src` из корня выбранного checkout. Зависимости разрешает `pip`;
код библиотеки использует их интерфейсы. Установленный wheel 1.0.0 и его
корневой launcher остаются прежними, исходники 2.0 не объявляются новым релизом.

## Ответственность модулей

`cli.main` читает CLI и печатает итог; `__main__` и два консольных имени вызывают
тот же вход. Корневой `start-app` выбирает собственную установленную `.venv`.
Npm объявляет собственный bin в package.json: npm-install.cjs создаёт venv/pip,
npm-start-app.cjs передаёт существующему CLI argv/cwd/env/stdio, npm-runtime.cjs
владеет тонкой границей процесса и сохранением обычного/сигнального исхода.
Доменные configuration/actions/preparation/checking от npm не зависят.
`catalogue` проверяет входную схему; `parameters` разрешает значения и подстановки;
`engine` выбирает действия по состоянию ресурса; `process` выполняет внешний процесс
и разбирает его ответ. Предметная логика обслуживания находится в этих владельцах,
а инструменты конкретной инфраструктуры задаются каталогом.

В исходниках разработки 2.0 `configuration.domain` владеет сопоставлением операции
и полным документом требований. `Requirements` обеспечивает уникальные IDs,
порядок, выборку, добавление, замену, удаление и очистку с сохранением непрозрачных
данных. Предметные изменения возвращают новые значения; домен не зависит от
файлового ввода, JSON Patch или CLI.

`configuration.application.read_operation_configuration` единообразно разрешает
выбранный документ для `ConfigurationReader` и `ConfigurationWriter`. Reader
использует переданный порт чтения; writer зависит от вызываемых портов чтения,
изменения выбранного объекта и сохранения. Он проверяет полный результат до
единственной записи. `configuration.json_patch` применяет стандартные
`jsonpatch`/`jsonpointer`, `configuration.json_file` публикует JSON через временный
файл в том же каталоге и замену выбранного файла. Команды остаются данными.

Композиция `configuration` подставляет существующий `catalogue.read_json` и
адаптеры записи при вызове writer; путь чтения и CLI не загружает ненужные им
адаптеры. Корневой пакет экспортирует две функции чтения и четыре записи.
Этот путь не вызывает `load_catalog` или `engine`. Полные пользовательские
договоры: [чтение](configuration-reading.md#библиотека-чтения) и
[запись](configuration-editing.md#библиотека-записи).

Изменение поведения разрабатывается через TDD: согласовать проверку, написать
воспроизводящий тест и подтвердить RED, независимо проверить тест, реализовать
поведение, подтвердить GREEN и передать точную ревизию на независимую проверку.
Исправление принятого теста согласуется с проверяющим отдельно от реализации.
Документация обновляется по фактическому принятому поведению.

`actions.domain.validate_command` задаёт единые правила исходных и подставленных
команд; `interpreted_result` проверяет ответ обработчика. `actions.application`
подготавливает всю цепочку через стандартный `Template` до эффектов; подставленные
обязательные поля проверяются до разрешения cwd. `ActionExecutor` зависит
от портов процесса и `ResultInterpreter`.
`actions.process` использует стандартный `subprocess.run` с полными bytes;
`actions` компонует публичные функции и конкретный адаптер. Домен зависит внутрь,
а не от CLI/файлов/процесса. Это отдельный от прежнего catalog/v2 договор;
чтение/запись конфигурации переиспользуются без копирования их правил.
[Полные API и примеры](action-execution.md#библиотека-исполнения) описывают
фактическую исходную возможность, не новый релиз или изменение старого CLI.

`preparation.application` владеет последовательностью выбранных требований:
переданные порты чтения, планирования и исполнения переиспользуют configuration
и actions. Общая проверка parameters/base_dir/interpreters принадлежит
`actions.application.validate_execution_inputs` и выполняется также для пустой
выборки. Все выбранные цепочки планируются до первого процесса; результат содержит
только попытанные требования и полную частичную работу до первого неуспеха.
Отдельный доменный aggregate или второй исполнитель команд для этого не вводится.

`actions.transport` — общий владелец загрузки готовых обработчиков через importlib,
обычных JSON-ответов, JSON-safe планирования и base64-доставки rawstreams.
`preparation.cli` и `checking.cli` используют его без второго загрузчика или кодека.
Библиотечные композиции сохраняют непрозрачные Python-значения.
`preparation.presentation` и `checking.presentation` обходят собственные формы
итога, делегируя доставку action единому владельцу. Прежний private модуль
заменён этим владельцем и не предоставляет совместимого alias.
`cli.main` явно выбирает infra/deps/adjust и check/run с одним объявленным
источником, не угадывая формат. Configured run использует прежний
`run_preparation`/reader/planner/executor; явный catalogue run сохраняет свой договор.
[Полные входы и инструкции](resource-preparation.md#подготовка-ресурсов)
описывают фактическое source-расширение, не установленную пакетную поставку.

`examples/process-launch/start_console.py` — отдельный внешний инструмент:
`main` владеет аргументами/JSON/диагностикой, `_submit_command` открывает
binary append-логи и передаёт argv в Popen. Ядро не импортирует этот пример.
Непосредственный PID/submitted/EOF отделены от времени жизни/готовности worker;
терминал и его PTY выбираются конфигом. Нет нового supervisor или второго
исполнителя. [Полный договор и правильные сценарии](process-launch.md#запуск-процессов).

`examples/settings-alignment/align_queue.py` принадлежит обслуживаемому примеру:
`queue_value` читает выбранную позицию стандартным JSON Pointer, `align_queue`
выполняет пакетное чтение, точечные публичные update и подтверждающее перечитывание,
`main` доставляет CLI/JSON. Правило равенства очередей не находится в общем ядре.
Две публикации не являются общей транзакцией; обычный неуспех сохраняет фактическую
частичную работу. [Полный договор и инструкция](settings-alignment.md#согласование-настроек).

`checking.domain` владеет обязательным presence и предоставляемым availability.
`checking.application` читает все три документа и планирует все объявленные
действия до процессов, выполняет условные проверки и продолжает независимые
ресурсы/дополнительные условия. Он сохраняет источник/ID, попытанные результаты
и отдельные непроверенные состояния. Composition использует существующие
reader/planner/executor, а не изменяет fail-fast preparation.
`examples/resource-checking/check_settings.py` принадлежит обслуживаемому примеру:
проверяет реальный файл/JSON и две непустые queue strings через публичное
пакетное чтение/стандартный Pointer, ничего не записывает.
[Полный договор и инструкция](resource-checking.md#проверка-окружения).

### Реальные консоли и документация запуска

39 проверок `tests/test_process_launch.py` требуют подготовленной X11-среды:
Zutty, DejaVuSansMono, libX11, ImageMagick `import`/`identify`, `xwininfo`,
`setxkbmap` и Xephyr. Их предоставляет оператор выбранной Linux-среды через
её пакетный менеджер. `ENV2_XEPHYR_ROOT` указывает на подготовленный корень
с `usr/bin/Xephyr` и `usr/lib/x86_64-linux-gnu`: `/` для системной установки
либо собственный корень распакованного пакетного набора.
[Технические условия arrangement](../tests/fixtures/process-launch/README.md)
отделяют ошибки подготовки от продуктового RED. В выбранном checkout:

```bash
: "${app_python:?Выберите подготовленный Python}"
: "${DISPLAY:?Выберите доступный X11 display}"
: "${ENV2_XEPHYR_ROOT:?Выберите подготовленный корень Xephyr}"
DISPLAY="$DISPLAY" ENV2_XEPHYR_ROOT="$ENV2_XEPHYR_ROOT" PYTHONPATH=src \
  "$app_python" -B -m pytest -p no:cacheprovider -q \
  --basetemp build/process-launch-check tests/test_process_launch.py
```

Три случая используют собственный видимый Xephyr и реальные PTY/input/Ctrl+C.
Private display не доказывает исключительность ввода: для точного автоматического
ответа наблюдайте события своих окон и учитывайте внешний ввод. Непустые PNG,
данные процессов, фактические ответы и закрытие своих ресурсов — разные проверки.
Дополнительный неуспешный опыт остаётся неуспешным; источник лишних событий
не приписывается участнику без доказательства. Эталон не ослабляется ради PASS.

Новые правильные [четыре инструкции](process-launch.md#пошаговая-инструкция)
исполняются на собственных рабочих копиях: CLI all, API subset, empty selection
и direct tool. Проверка ссылки сама не доказывает исполнение. Общие guard/smoke
выбираются по затронутым границам; выпускная сборка остаётся отдельной работой.
Сохраняйте полные результаты/source hash до очистки своих данных.

При разработке с Poise используется его существующий владелец локальных ссылок;
это инструмент разработки, а не зависимость поставляемого приложения:

```bash
PYTHONPATH="$poise_root/src:$poise_root" "$poise_python" -P -s -B \
  "$poise_root/tools/check_documentation.py" --checkout "$PWD" \
  --changed docs/process-launch.md --changed README.md
```

Передайте выбранные пути `poise_root`/`poise_python` своей установки. Checker
проверяет также входящие ссылки на изменённые страницы. Добавляйте остальные
изменённые Markdown через повторяемый `--changed`; смысл и команды проверяются
отдельно. Единственный AI-скилл проверяется штатным skill-creator validator
в среде AI; он ссылается на канонические человеческие инструкции.

### Прежние узкие наборы

15 проверок согласования подтверждают выбранные значения, фактические внешние
процессы, сохранность данных, полные/частичные итоги и общие входные границы.
Walkthrough согласования выполняет четыре корректных сценария на своих копиях.

45 проверок checking подтверждают реальные условия/процессы, исходники ресурсов,
полные bytes, непрозрачный API, JSON CLI, независимое продолжение, непроверенные
состояния и полный preflight. Walkthrough проверки исполняет семь правильных
сценариев на собственных копиях. Код и документационные примеры проверяются
узко вместе с прежними границами и maintained smoke, не выпускной сборкой.

Модуль исполнения содержит 114 случаев: подготовка/реальные процессы/полные bytes,
смена обработчика и диагностируемые отказы с сохранностью частичной работы.
Walkthrough исполняет [четыре корректных сценария](action-execution.md#пошаговая-инструкция)
на собственных временных данных. Для изменения исполнителя обычный узкий набор:
этот модуль, 116 проверок записи, 30 чтения и 24 smoke; выпускная сборка отдельно.

Узкие файлы содержат 30 случаев библиотечного чтения и 116 случаев записи:
четыре операции, точечные изменения, сохранение остальных данных, контекст
ошибок и обычные файловые отказы. Используются независимые JSON fixtures
и проверки свежести обоих документов. В дочернем checkout вместо
`.venv/bin/python` явно выберите подготовленный интерпретатор приложения;
`PYTHONPATH=src` должен указывать на исходники именно проверяемого checkout.
Рабочий установленный wheel ради проверки исходников не переустанавливается.
Единственный AI-скилл хранится в `.agents/skills/environment-maintenance/SKILL.md`.
Состав текущего npm-кандидата, включая этот скилл и документы, проверяется
настоящим pack/install по [пакетной инструкции](npm-distribution.md#пакетная-поставка-npm).

Исторический выпускной набор 1.0.0 содержит 29 случаев: версия, аргументы и результаты обоих входов,
реальная сборка wheel/sdist, установка wheel в собственную `.venv` временного
потребителя, наличие собственных документации/тестов в исходном архиве и
сохранение действующего каталога v2. Smoke содержит 24 случая; две проверки
документационного договора дополняют содержательное чтение инструкций.
Последовательные запуски сборочных тестов используют разные `--basetemp`, если
нужно сохранить предыдущие результаты. Одновременно запущенные сборки одного
исходного дерева не являются способом проверки поставки.

Для обычного изменения выполняйте затронутые узкие проверки и поддерживаемый
smoke; сборочные 29 случаев выше относятся к отдельной проверке выпуска.
Проверка текста или ссылки не доказывает исполнение команды: выполните
примеры [чтения](configuration-reading.md#пошаговая-инструкция) и
[записи](configuration-editing.md#пошаговая-инструкция) на выбранных исходниках.
При выпуске отдельно выполните установку и примеры `--version`/`check` по
[инструкции](installation.md), в том числе из постороннего cwd.
Проверьте локальные ссылки, точные заголовки и входящие ссылки
применяемым инструментом проверки документации проекта, а смысл — по коду и
полным результатам. Исторические сценарии восстановления прежних выпусков
сохранены в `tests`; их наличие не означает выполнение в новом выпуске.

## Локальный npm-кандидат 2.0.0

[Полная инструкция](npm-distribution.md#пошаговая-инструкция) использует стандартные
pack/install и отдельный prefix. Помимо Python/dev prerequisites требуются
Node22/npm10. Пакет содержит docs/tests/examples/один skill; готовый runtime,
build/dist/logs/рабочие конфиги в архив не входят. Зависимости экземпляра
устанавливает pip из pyproject, JS-зависимостей нет.

Для обычной проверки поставки выбираются tests/test_npm_delivery.py (23 случая),
прежние process_launch39/resource_checks45/settings_alignment15/
resource_preparation62 и maintained smoke24. Перед пакетными тестами задайте
ENVIRONMENT_MAINTENANCE_PYTHON, собственные ENV2_PACKAGE_TEST_ROOT и подготовленный
ENV2_PACKAGE_WHEELHOUSE с реальными build/runtime колёсами. Это условия стенда,
не новые обязательные настройки продукта. Полные внешние captures и closure
сохраняются тестовым владельцем. Три CJS проверяются стандартным node --check.

При проверке новой ревизии сохраняйте commit/tree, argv/cwd, полные stdout/stderr,
digest реального tgz и identity установленного runtime/core/библиотек. Отдельно
подтверждайте передачу child signal, включая SIGPIPE/SIGUSR1 и отсутствие debugger,
обычные коды и spawn-error причину. Новый doc commit требует свежего pack/установки
и доказательств, даже при неизменном Python-коде. Два адресных документационных
случая tests/test_v2_documentation.py дополняют существующий link checker и
skill-creator validator; они не заменяют смысловую проверку инструкций.

Окончательные tgz и отдельная квитанция содержат фактические source/tree/digest,
версию, среду, команды и проверки. Квитанция лежит вне описываемого архива.
До удаления временных материалов передайте пакет и доказательства в постоянное
хранилище; при работе через Poise используйте его artifact/delivery владельцев.
Локальный проверенный кандидат не означает npm publish, Git tag или push.
Последующие потребители устанавливают выбранные байты и обновляются отдельно.

## Сборка и поставка

Следующая процедура относится к выбранной релизной ревизии 1.0.0. Разработка
новых API в `master` не переиздаёт этот релиз: новую версию и её поставку
готовит отдельный процесс выпуска после завершения соответствующей разработки.

Зафиксируйте точную ревизию исходников, включая документы. Стандартная сборка
в подготовленном окружении:

```bash
.venv/bin/python -m build --no-isolation --outdir dist/1.0.0
sha256sum dist/1.0.0/environment_maintenance-1.0.0-py3-none-any.whl \
  dist/1.0.0/environment_maintenance-1.0.0.tar.gz
```

Исходный архив включает корневой вход, исходники, README, `pyproject.toml`,
примеры, документацию и тесты. Wheel предназначен для установки: собственные
консольные входы создаёт `pip`. Проверяйте те же выбранные байты пакетов, которые
передаются получателю, а не только заново собранный аналог.

Изменение документации после сборки требует новой сборки исходного архива и
новых доказательств для окончательной ревизии. Сохраните отдельно от архивов
квитанцию: версия, точный commit/tree и tag, имена и SHA-256 wheel/sdist,
инструменты и команды сборки, полные stdout/stderr и результаты проверок,
приёмка и интеграция. Свяжите содержимое модулей wheel и исходного архива с
этой ревизией. Квитанция не включается внутрь архива, чей digest она описывает.

После независимой приёмки интегрируйте принятую ревизию в основной checkout.
Установите выбранный wheel в его собственную `.venv` и проверьте корневой
`start-app --version` и `check`. Успех временного потребителя не заменяет этот шаг.
Создайте локальный tag `v1.0.0` на точной интегрированной ревизии после проверки,
что такого tag ещё нет. Сохраните wheel/sdist, квитанцию и журналы в постоянном
каталоге `dist/1.0.0` самостоятельного приложения до удаления материалов задачи.

Локальная поставка — отдельный результат после сборки, проверки, приёмки,
интеграции и подтверждения установки. Текущий способ передачи — этот комплект
файлов; публикация в реестре и отправка Git в сеть являются отдельными действиями.
Правила изменения версии определены в [README](../README.md#версионирование).

# Использование и конфигурация

## Команды и аргументы

[Пошаговая инструкция CLI](#пошаговая-инструкция-cli).

| Команда | Назначение | Применимые переопределения |
|---|---|---|
| `infra`, `deps`, `adjust` | Объявленное обслуживание | `--config`, `--parameters`, `--base-dir`, `--requirements` |
| `check` | Presence/availability/связанные условия | `--config`, `--parameters`, `--base-dir` |
| `run` | Запуск с учётом PGID | `--config`, `--parameters`, `--base-dir`, `--env`, `--app` |
| `run list` | IDs доступных APP | `--config`, `--env` |
| `stop`, `stop list`, `stop all` | Просмотр/остановка сохранённых групп | `--env`, `--app` по формам ниже |

`-h`/`--help` и `--version` доступны без исполнения рабочих действий. Неизвестные аргументы предупреждаются в stderr и пропускаются; они не создают дополнительный режим. Используйте перечисленные флаги. Прежний `--dry-run` не обеспечивает preview.

`--requirements` принимает `all` либо JSON-массив уникальных строковых IDs. Без него infra/deps/adjust выбирают все записи. Повтор ID в selection или документе отвергает весь запрос до команд; неизвестный CLI ID предупреждается и пропускается. Порядок выбранных IDs сохраняется. У [SDK](configuration-reading.md#публичный-договор) неизвестный ID — ошибка.

Main по умолчанию — `CWD/start-app.json`. Относительные paths в `operations` и `invocation` считаются от main, явные CLI paths — от cwd. [Профиль](persistent-entry.md#поля-постоянного-профиля) задаёт parameters/base_dir; полностью явному вызову invocation не нужен. `base_dir` — абсолютная база cwd внешних команд.

## Пошаговая инструкция CLI

Сначала [подготовьте профиль](persistent-entry.md#пошаговая-инструкция). В каталоге приложения:

```bash
start-app --version
start-app --help
start-app infra
start-app deps
start-app adjust
start-app check
start-app run list
```

Ресурсы и допустимый порядок обслуживания задаёт приложение. Для требования `assets` вашего infra документа:

```bash
start-app infra --requirements '["assets"]'
```

`[]` выбирает пустой список, `["all"]` — буквальный ID `all`.

## Именованные run и stop

Ниже альтернативные формы, а не обязательная последовательность:

| Форма | Результат |
|---|---|
| `run` | Все APP в новой UUID-среде |
| `run --env ENV` | Все APP в именованной среде |
| `run --app APP` | Один APP в новой UUID-среде |
| `run --env ENV --app APP` | Один новый APP в этой среде |
| `run list` | Все IDs run конфигурации |
| `run list --env ENV` | IDs конфигурации, ещё не зарегистрированные в найденной ENV |
| `stop` или `stop list` | Просмотр всех записей реестра |
| `stop list --env ENV` | Просмотр указанной ENV |
| `stop --env ENV` | SIGTERM всем сохранённым группам ENV |
| `stop --env ENV --app APP` | SIGTERM одному APP |
| `stop all` | SIGTERM всем группам всех читаемых ENV |

Для stop выбор APP требует ENV. `APP=all` — буквальный ID; для всех APP опускают `--app`. Имя ENV `all` зарезервировано; используйте, например, `dev-1`. Полные правила и [пример](process-launch.md#пошаговая-инструкция) принадлежат [договору процессов](process-launch.md#запуск-процессов). Stop читает сохранённый реестр OS temp, а не main/parameters.

## Результат и повторный запуск

Вывод содержит полный JSON; stdout/stderr команд передаётся в base64 по [договору transport](action-execution.md#итог-исполнения). У run/stop успех даёт exit0, операционный отказ — exit1, ошибки аргументов/входов — exit2. У run при допустимом имени ENV входная ошибка сохраняет JSON с адресом и деталями; argparse-отказ может ограничиться stderr. Подготовка/check имеют собственные [подробности результата](resource-preparation.md#результат-и-диагностика).

Повтор — новое явное действие. Сначала прочитайте полный результат и фактические эффекты. Для частичного запуска используйте `run list --env ENV` и точный APP. [Восстановление](migration-v4.md#ручное-восстановление) сохраняет остальные приложения и записи.

# Переход на environment-maintenance 4.0.0

[Текущий CLI](configuration.md#команды-и-аргументы), [run/stop](process-launch.md#запуск-процессов) и [выбор установки](npm-distribution.md#собственная-зависимость-приложения) задают рабочий договор. Переход подготавливается отдельно для каждого приложения; source candidate не переключает действующую установку.

## Переход конфигурации

| Прежнее представление | Представление v4 |
|---|---|
| `operations.run` → документ requirements | Тот же mapping → документ applications |
| `invocation.requirements` | Согласованный фактический состав документов; CLI default all |
| Run selection через requirements | Один `--app APP` либо все APP без этого флага |
| Прежний каталоговый check/run | Явные configured infra/deps/adjust/check/run и stop |
| Последний reply launcher с pid | Raw JSON submitted с положительным integer pgid |
| Рабочий импорт/копирование examples interpreter | Qualified стандартный либо собственный versioned application module |
| Launcher file из examples | Installed maintenance Python и module entry |

1. Установите фактическую выбранную версию и сохранённый состав обслуживания текущего приложения. До удаления invocation.requirements материализуйте именно выбранные IDs в документах в согласованном порядке. Исключённые requirements остаются исключёнными, остальные операции сохраняют массив requirements.
2. Переведите только run на applications. Проверьте уникальность IDs и каждой selection. Сохраните argv/cwd/env, target каждого APP, plugin options и нужный value contract. Для нескольких выбранных APP можно последовательно добавить их в одну ENV через `--app`; полный запуск выбирает весь согласованный документ.
3. Выберите установленный maintenance Python отдельно от Python приложения. Его launcher вызывается так:

```text
MAINTENANCE_PYTHON -I -B -m environment_maintenance.running.console --stdout-log OUT --stderr-log ERR -- EXECUTABLE ARG...
```

4. Если достаточно проверки exit code, main связывает готовый объект:

```json
{"interpreters":{"exit":{"module":"environment_maintenance.actions.interpreters","attribute":"exit_result"}}}
```

Команда выбирает `interpreter.name=exit` и `options.accept`, например `[0]`. Стандартный value — исходный exit code; прикладной value/schema сохраняет собственный обработчик приложения. ERP/Poise команды и правила остаются у их владельцев.

5. Подготовьте согласованные archive/version/lock и v4 конфигурации. После явного разрешения владельца переключите выбранную установку и профиль одним согласованным изменением; подтвердите actual version/prefix/module identity, публикацию профиля, meanings и safe run/list/stop. [Npm-процедура](npm-distribution.md#собственная-зависимость-приложения) сохраняет другие экземпляры.

Неизвестные CLI arguments v4 предупреждаются/пропускаются. Старый dry-run флаг не даёт preview и не подавляет запуск. Исправьте вызывающие команды по справочнику до переключения. На обычном пути не добавляются automatic preparation, health, retry или rollback.

## Четыре потребителя

| Владелец | Согласованный v4 результат |
|---|---|
| ERP platform-infrastructure | Versioned `config/dev/start-app/v4`, семь APP с собственными run-process targets; main/parameters для local-v4 либо native publication. Generic interpreter из package. |
| Poise-op | `config/maintenance/start-app/v4`: operations включая adjust, applications и bootstrap без run requirements; native operator profile выбирает эти документы. |
| Stride | Отдельный operator v4/stride profile, прежний selected-poise-cli target/context и собственные repository/runtime bindings. |
| Workspace-recover | Отдельный operator v4/workspace-recover, прежний Node/script/--help, applications и selected maintenance Python. |

Native operator v4 публикуется в постоянной области владельца, не под удаляемой Task. Source templates, module/entry paths и готовые callbacks должны принадлежать выбранной совместимой supply. Shared archive/wheelhouse допустимы; установленный экземпляр остаётся собственным у приложения. Старые работающие selections обновляются отдельно.

ERP3.1.0 использовал postinstall, копирующий учебный interpreter в site-packages собственного SDK. При выборе4 в едином изменении manifest/lock/config уберите этот postinstall до npm install/ci: v4 уже поставляет стандартный модуль. Подготовленный removal patch относится к согласованному v4 переходу; отдельно к действующему3 его не применяют. Сам файл в site-packages был установленной копией, а не постоянным источником реализации. Обязательный source принадлежит Git/поставке, установленная копия восстанавливается package manager.

Отсутствующий adjust mapping и устаревшие позиционные ERP edits исправляются в v4 источниках владельца конфигураций. Их публикация/проверка не подтверждает исправление ещё выбранного старого профиля. Активные проявления учитывает known-bugs владельца Poise-op operator, вместе с Task исправления; после подтверждённого устранения активного условия запись снимается.

## Ручное восстановление

Сначала прочитайте полный JSON, stderr, фактический `file`, `file_exists`, APP results и PGID. Адрес/владельца конкретного объекта определяют по этим данным, а не по похожему имени процесса. Реестр находится в OS temp/environment-maintenance; используйте тот же TMPDIR, что при запуске.

| Наблюдение | Действие владельца и подтверждение |
|---|---|
| Начальная запись/close отказала, file_exists=false, APP не запускались | Устранить конкретную причину ФС/quota/доступа; повторить новый явный run. Остальные файлы не удаляются. |
| Ответ сохранил исходную и cleanup ошибки, file_exists=true, новая резервация пустая/частичная, APP не запускались | Исправить причину cleanup. Подтвердив по receipt владение именно новой резервацией, удалить только её указанный path. Проверить stop list и следующий собственный run. |
| Процесс передан, PGID в ответе, но сохранение mapping отказало | Сохранить фактический PGID и проверить свои эффекты. Исправить доступ/ФС; владелец восстанавливает достоверную запись по receipt либо явно останавливает только свою известную группу. Повторять run поверх неизвестного исхода нельзя. |
| Stop сообщил ошибку сигнала или удаления записи | Прочитать полную причину; failed mapping сохраняется, остальные цели могли уже остановиться. Устранить причину и повторить stop для конкретной ENV/APP. |
| Повреждённая/нечитаемая запись | Исследовать точный path и его владельца. Читаемые другие ENV доступны stop; создание новых имён может отказываться, пока доступность имени нельзя установить. Восстановить только известные payload/PGID либо убрать подтверждённую собственную незавершённую резервацию. |
| Реестр утрачен при очистке OS temp | Идентифицировать собственные запуски по сохранённым receipts/логам. Восстановить только подтверждённые группы или завершить их вручную своим OS-инструментом; угадывание PGID не восстанавливает учёт. |

Формат записи приведён [в договоре](process-launch.md#реестр-окружений). Name берётся из payload; имя файла само не подтверждает ENV. Соседние APP, записи и работающие процессы сохраняются. Массовая очистка temp, автоматический ремонт и обязательный архив checkpoint не являются процедурой восстановления. Завершённая передача запуска не является health proof; успешный SIGTERM не означает ожидание завершения.

## Возврат выбранной поставки

Владелец согласует прежний retained archive/lock и соответствующие ему конфиги, затем восстанавливает собственную установку штатным npm ci/install с нужным Python. Рабочие данные/другие приложения сохраняются. Сначала проверьте version/prefix и доступность инструментов. Текущие v4 registry records не преобразуются в старый CLI автоматически; собственные живые v4 группы обрабатываются по их реальному учёту до смены управляющего инструмента. Фактическая интеграция и обновление остаются отдельно разрешёнными действиями.

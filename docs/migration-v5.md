# Переход 4.x → 5.0.0

## Изменение договора

В версии 5 `run list` возвращает объект по имени приложения вместо массива ID. Каждая запись содержит `pgid: null` и разрешённые требуемые ресурсы. В `stop list` запись содержит положительный PGID и сохранённые ресурсы конкретного запуска. Это несовместимое изменение CLI: потребитель прежнего массива должен перейти к именованным записям. Полные формы, примеры и диагностика принадлежат [договору процессов](process-launch.md#ресурсы-приложения).

SDK `list_requirement_ids` продолжает возвращать ID, `read_requirements` — полные буквальные объекты. Ответ `run` сохраняет массив попыток запуска. Настройки вывода также прежние: без `--output` одна строка, голый `--output` включает pretty. Изменение представления не меняет данные.

## Переход конфигурации

1. Выберите обслуживаемый экземпляр и его постоянные main/run/parameters. Сохраните возможность восстановить прежнюю выбранную поставку; отдельный архив рабочей задачи не требуется.
2. В APP добавьте необязательное `resources` по [схеме](process-launch.md#ресурсы-приложения): host/port для сетевого сервиса, источник queue для worker, application/command для scheduler. Используйте те же параметры, что реально получают команды. Не выводите значения из похожих имён процессов и не добавляйте неприменимые поля.
3. Выберите тот же invocation/parameters/base-dir для просмотра и запуска. Любой ключ `resources`, даже `{}` или литеральные значения, требует обычного контекста параметров. Без ключа прежний просмотр не требует parameters. Доступность проверяется отдельным `check`; декларация ресурсов сама не добавляет проверок.

Приложение без `resources` получает только `pgid: null` в required map; после запуска — только PGID. Старое имя конфигурации или версия пакета сами не создают описаний очередей/портов. Заполняет их владелец приложения из его реального runtime.

## Совместимость учёта

Формат реестра сохраняет `format-version: 1`, дополнительные поля находятся в строке APP рядом с PGID. Версия 5 читает прежние PGID-only записи и сохраняет полные соседние строки при добавлении/удалении APP. Сохранённый marker не используется как проверка равенства1. Ресурсы старого запуска остаются неизвестными, если их не записали тогда. Не восстанавливайте их из новой конфигурации.

`stop list` и stop работают без main/parameters; даже их удаление не меняет снимок. Это регистрационный учёт, а не доказательство текущего здоровья/занятости сокета. Успех stop подтверждает отправку SIGTERM, а не ожидание завершения группы. [Ручное восстановление](migration-v4.md#ручное-восстановление) остаётся у прежнего владельца процедуры.

Старый 4.x writer при перезаписи может потерять новые поля ресурсов. Совместное изменение новых записей старым и новым инструментом не гарантирует сохранность метаданных. Обслуживайте такие записи версией 5; не очищайте общий OS temp для смены версии.

## Пошаговая поставка

1. Получите из действующего владельца развёртывания перечень всех фактических потребителей и их самостоятельных установок. Несколько регистраций могут использовать одну копию, а одно приложение — несколько разных. Данная инструкция не создаёт второй статический реестр.
2. Выберите принятую поставку 5.0.0. Локальная сборка/установка, публичная публикация и скачивание из реестра — разные результаты. Для публичного выпуска проверьте [скачанные байты](npm-distribution.md#публичная-версия-и-обновление-потребителей) против выданного архива; затем используйте выбранные точные байты, а не случайный latest.
3. Последовательно обновите каждую установку через её владельца. Согласованно сохраните manifest, созданный npm lock и выбранный архив в постоянной области приложения вне disposable Task-root. Выполните [штатную установку](npm-distribution.md#собственная-зависимость-приложения) с нужным Python и индексом/retained wheelhouse. Для исходного root entry отдельно переустановите пакет в его собственную соседнюю `.venv`: изменение src не обновляет установленную копию.
4. Проверьте собственный entry `--version`, собственные `sys.executable`, `sys.prefix`, `environment_maintenance.__file__`, module/distribution version5.0.0 и manifest/lock/digest. Пример проверки origin находится [у установки](npm-distribution.md#собственная-зависимость-приложения). Успех чужой копии не подтверждает этот экземпляр.
5. Проверьте его рабочий `run list` на согласованных ресурсах и безопасный собственный тестовый запуск, затем `stop list` с фактическим PGID/снимком и выбранный stop. Используйте отдельные ENV/логи и подготовленные ресурсы; не останавливайте чужие группы. Сохраните реальные выводы и подтвердите завершение своих процессов отдельным наблюдением. Владелец окружения выполняет применимые check и совместимость своего binding.

Квитанция поставки хранит source/commit/tree, версию и digest, установленные пути, полные исходы и действительные проверки каждой копии. Публикация не обновляет потребителей автоматически. Интеграция исходников, поставка всем обязательным потребителям и очистка временных ресурсов выполняются своими владельцами; материалы нужны до подтверждения обязательных получателей. Документация процедуры сама по себе не подтверждает выполнение этих действий.

## Возврат выбранной поставки

Согласуйте прежние retained archive/manifest/lock и конфигурацию владельца приложения. Сначала сохраните возможность обслужить новые записи инструментом 5 либо штатно завершите принадлежащие им запуски до возврата управляющего writer. Восстановление старой установки не превращает неизвестные старые ресурсы в известные и не даёт старому writer гарантию сохранности новых полей. Сохраняйте соседние записи/данные; при неопределённом исходе используйте [receipt и ручное восстановление](migration-v4.md#ручное-восстановление), а не угаданный PGID или массовое удаление temp.

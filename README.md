# environment-maintenance 0.2.1

Самостоятельное приложение для проверки и обслуживания окружения по каталогу
`environment-maintenance/catalog/v2`. Пакет не импортирует `ai-poise`, не читает его
базу и не меняет его конфигурацию. Оператор явно выбирает один каталог v2 для каждого
запуска.

Требуется Python 3.11 или новее. Runtime-зависимостей нет.

Поведение версии 0.2.1 проверено в Ubuntu WSL2, Linux/POSIX, на Python 3.13.15.
Минимальная версия в метаданных пакета не означает проверку всех версий Python и
операционных систем.

Комплект локальной поставки содержит `manifest.json`, wheel
`environment_maintenance-0.2.1-py3-none-any.whl`, `source.bundle`,
`build-record.json`, `build.stdout` и `build.stderr`. Манифест связывает версию,
commit исходников, контрольные суммы wheel и исходного bundle с фактической записью
сборки и полными журналами. Сверьте выбранные файлы с манифестом перед установкой.
Из каталога поставки в явно выбранное Python-окружение:

```bash
python3 -m pip install --no-index --no-deps \
  ./environment_maintenance-0.2.1-py3-none-any.whl
```

Эта команда устанавливает локальный файл; доступность пакета в публичном индексе
не требуется.

## Запуск

Из корня исходников:

```bash
PYTHONPATH=src python3 -B -m environment_maintenance check \
  --catalog-dir examples/catalog-v2

PYTHONPATH=src python3 -B -m environment_maintenance run \
  --catalog-dir examples/catalog-v2

PYTHONPATH=src python3 -B -m environment_maintenance run \
  --catalog-dir examples/catalog-v2 \
  --dry-run
```

После установки дистрибутива те же операции доступны через команду
`environment-maintenance`. Поддерживаются только подкоманды `check` и `run`, а также
аргументы `--catalog-dir`, повторяемый `--values`, повторяемый `--set` и `--dry-run`.

`check` и `run --dry-run` никогда не вызывают `install` или `repair`. Обычный `run`
может выполнить ровно действие, выбранное состоянием проверки, после чего всегда
повторяет тот же `check`.

## Каталог v2

`--catalog-dir` указывает на существующий каталог, содержащий единственный манифест
`catalog.json`. Его верхний уровень имеет точные поля:

```json
{
  "schema": "environment-maintenance/catalog/v2",
  "parameters": {},
  "inherit_env": ["PATH"],
  "requirements": []
}
```

Неизвестные или отсутствующие поля, повторяющиеся JSON-ключи, неизвестная schema и
неверные типы отклоняются до запуска действий. Каждый элемент `requirements`
содержит уникальный `id` и три обязательных действия: `check`, `install`, `repair`.
Порядок массива является порядком выполнения.

Каждое действие задаётся всеми следующими полями:

```json
{
  "argv": ["python3", "probe.py", "check"],
  "cwd": ".",
  "env": {},
  "output": {
    "schema": "environment-maintenance/action-result/v2"
  },
  "max_output_bytes": 4096,
  "execution_bound_seconds": 5
}
```

`argv` передаётся процессу напрямую: shell не запускается и строка команды не
интерпретируется. Относительный `cwd` считается от выбранного каталога v2. Дочерний
процесс получает только переменные из `inherit_env`; значения из `action.env`
добавляются после allowlist и заменяют одноимённые унаследованные значения.

`max_output_bytes` ограничивает сохраняемый объём каждого потока stdout/stderr.
`execution_bound_seconds` ограничивает время действия. При превышении ограничения
процесс и его группа завершаются, а результат остаётся ошибкой протокола. Ограничение
вывода не является дисковой квотой и не превращает частичный вывод в успех.

`max_output_bytes` — целое число от 1 до 16 777 216 включительно.
`execution_bound_seconds` — конечное целое или дробное число больше 0 и не больше
3600. Непригодные границы, включая слишком большое целое число, отклоняются как
ошибка входного контракта до запуска действий.

После подстановки параметров `argv`, `cwd` и значения `env` всех объявленных
действий проверяются на представимость для передачи операционной системе до
первого запуска. Непредставимый текст даёт объяснимую ошибку входного контракта.
В проверенном POSIX-окружении сохраняются допустимые имена с байтами, представленными
Python через `surrogateescape`, и символы Unicode вне основной многоязычной плоскости.

## Параметры

Параметры имеют тип `string`, `integer`, `number` или `boolean`. Декларация может
содержать `default`, имя переменной `env` и флаг `secret`. Значения выбираются в
следующем порядке приоритета:

1. `default` из `catalog.json`;
2. JSON-объекты из повторяемых `--values` слева направо;
3. явно объявленная переменная `env`;
4. повторяемые `--set name=value`.

Неизвестные имена, дубли одного имени в `--set` и значения неверного типа
отклоняются до действий. Подстановка `${name}` выполняется один раз во всех полях
требований; полученное значение повторно как шаблон не интерпретируется.
`secret: true` скрывает значение параметра в публичном JSON-результате. Секреты не
следует передавать через CLI, поскольку argv процесса доступен операционной системе.

Текст, который не передаётся в `argv`, `cwd` или окружение действия, сохраняется
как непрозрачное значение. Публичный JSON использует ASCII-экранирование: его байты
читаются как UTF-8, а после разбора JSON восстанавливаются исходные значения,
включая дополнительные символы Unicode и допустимый непрозрачный текст.

Неразбираемый `catalog.json` или документ `--values`, в том числе с вложенностью
выше возможностей текущего JSON-разбора, даёт контролируемую ошибку входного
контракта. Так же обрабатывается чрезмерно вложенный JSON для типов `integer`,
`number` и `boolean` из `--set` или объявленной переменной окружения. Фиксированный
предел вложенности форматом v2 не задаётся.

## Состояния и действия

Успешный `check` возвращает одно из четырёх состояний:

| Состояние | `check` и `run --dry-run` | `run` |
|---|---|---|
| `satisfied` | Итог `ready`, изменений нет | Итог `ready`, изменений нет |
| `missing` | Итог `action_required`, планируется `install` | `install`, затем тот же `check` |
| `invalid` | Итог `action_required`, планируется `repair` | `repair`, затем тот же `check` |
| `unavailable` | Причина и конкретные `recommendations`, изменений нет | Причина и конкретные `recommendations`, изменений нет |

Повторный `check` выполняется после каждой попытки `install` или `repair`, включая
неуспешную попытку. Успешное mutation-действие без последующего `satisfied` не
считается готовым окружением. Автоматических повторов, повышения привилегий и
необъявленных действий нет.

## Протокол действия

При exit code 0 stdout должен содержать ровно один UTF-8 JSON-объект заявленной
schema. Ответ `check` содержит точные поля `schema`, `requirement_id`, `action`,
`state`; для `unavailable` дополнительно обязательны непустая `cause` и непустой
массив непустых строк `recommendations`. Ответ `install` или `repair` содержит
`schema`, `requirement_id`, `action`, `outcome`, причём `outcome` равен `completed`.

Неверный exit code, лишние или пропущенные поля, несовпадающие ID/action/schema,
невалидный UTF-8/JSON, чрезмерная вложенность ответа, timeout и усечённый вывод дают
`protocol_failure`. Запись
результата сохраняет `invocation`, exit code, stdout/stderr, `capture_complete`,
`timed_out` и диагностическое `error`; такой результат никогда не считается
доменным состоянием.

При отказе обработки начального `check` данное требование получает `failed`, его
действие изменения не запускается; остальные требования каталога могут быть
обработаны дальше. При отказе обработки ответа `install` или `repair` выполняется
тот же исходный итоговый `check`. Даже если он обнаружил `satisfied`, отказ ответа
действия сохраняет итог `failed` и код 4: подтверждённое состояние ресурса и
успешность попытки обслуживания — разные сведения результата.

Итоговые коды процесса:

| Код | Результат |
|---|---|
| 0 | `ready` |
| 2 | `action_required` либо ошибка входного контракта |
| 3 | `unavailable` |
| 4 | `failed` |

Ошибка входного контракта печатается в stderr с кодом 2, пустым stdout и без запуска
дочернего процесса; существующие ресурсы сохраняются. Остальные итоги печатаются
одним JSON-объектом в stdout.

## Отказ и восстановление

При `unavailable` оператор устраняет указанную `cause` по сохранённым
`recommendations` и повторяет команду. При `protocol_failure` нужно проверить
сохранённые `invocation`, `error`, `timed_out`, `capture_complete`, stdout/stderr и
исправить само объявленное действие или его протокол. Runner не угадывает исправление
и не повторяет побочный эффект автоматически.

После ошибки входа исправьте указанный документ, типизированное значение, границу
или текст, передаваемый ОС, и повторите команду. После ошибки ответа действия
сначала прочитайте итоговую проверку и фактическое состояние ресурса: изменение
могло уже произойти. Исправьте протокол действия и только затем осознанно выбирайте
повторный запуск. Ошибка разбора начальной проверки не подтверждает состояние
соответствующего ресурса.

Рабочий пример находится в `examples/catalog-v2`: один каталог, один `catalog.json`
и самостоятельный `probe.py`. Он всегда сообщает `satisfied` и не является профилем
развёртывания `ai-poise`.

## Проверки

Выберите Python-окружение с `pytest`, доступными `venv`/`pip` и Git. В проверенной
сборке использован `setuptools 84.0.0`; он нужен для режима `build`, а не для
выполнения установленного приложения. Команды ниже выполняются из корня исходников
в Bash; `python3` должен обозначать выбранный интерпретатор.

Укажите абсолютный путь к рабочему каталогу результатов вне отслеживаемых
исходников. Пример `/absolute/path/to/release-output` замените своим путём.
Режим `build` собирает именно зафиксированный Git `HEAD`, поэтому изменения
исходников и README сначала должны быть зафиксированы.

111 целевых сценариев проверяют CLI исходников, реально установленный wheel и
происхождение поставки:

```bash
export ENV_MAINT_RELEASE_OUTPUT=/absolute/path/to/release-output
export ENV_MAINT_SUPPLY_MODE=build
PYTHONPATH=src python3 -B -m pytest -p no:cacheprovider -q -s \
  tests/test_v2_failure_recovery.py \
  tests/test_v2_release_recovery.py
```

Тесты выводят `ENV_MAINT_SUPPLY_MANIFEST` с путём к фактически созданному манифесту.
Для независимой проверки уже выбранного комплекта используйте `consume`: этот
режим сверяет и устанавливает те же байты поставки, не пересобирая wheel.
Каталог `ENV_MAINT_RELEASE_OUTPUT` должен существовать и быть доступен для записи;
в нём создаётся отдельное окружение установки. Замените пример пути к манифесту
точным путём выбранного комплекта и повторите ту же целевую команду pytest:

```bash
export ENV_MAINT_SUPPLY_MODE=consume
export ENV_MAINT_SUPPLY_MANIFEST=/absolute/path/to/supply/manifest.json
```

Поддерживаемый быстрый набор из 24 сценариев и две проверки документационного
договора дополняют целевой набор до 137 сценариев:

```bash
bash tests/smoke.sh python3

PYTHONPATH=src python3 -B -m pytest -p no:cacheprovider -q \
  tests/test_v2_documentation.py
```

Проверки происхождения сопоставляют семь Python-модулей wheel с указанным commit,
метаданные, CLI, исходный bundle, запись сборки и полные журналы. Текстовые проверки
README не заменяют содержательный осмотр документации по коду и результатам.
Созданные тестами файлы являются материалами проверки; окончательная приёмка и
передача выбранного комплекта выполняются отдельно.

Форматы `requirements.json`, `repairs.json`, флаг `--repairs`, вторичный файл
маршрутизации и поле/режим `apply` не входят в v2 и не распознаются приложением.
